# 调度网页与两套网络的分工

## 2026-11-09 实测

目标为服务方提供的 `http://223.108.218.59:3001/login`。

| 路径 | 结果 |
|---|---|
| 本机 HTTP 直连，显式绕过代理 | TCP 连接超时，HTTP 000 |
| 本机显式经过已启用的 SakuraCat HTTP 代理 | HTTP 502 |
| 已认证的盐城登录节点直连该地址 | 请求超时，HTTP 000 |
| SSLVPN + SSH/SFTP 到计算集群 | 正常，可读取队列、模块和 online1 |

这说明当前网页不可达不能仅归因于浏览器缓存或 SakuraCat；也不能据此断言整个服务对所有网络均已停机。需要服务方核对入口地址/端口是否仍有效、服务健康状态、来源 IP 白名单和防火墙规则。网页管理台和 Slurm/SSH 是不同入口，网页打不开不等于 Slurm 集群不可用。

当前 SSLVPN 路由覆盖 `174.0.250.0/24`，VPN 网关地址有单独的外网路由；没有观察到调度网页 IP 被 SSLVPN 接管。SakuraCat 是 Windows HTTP 系统代理，SSH/SFTP 在当前配置下仍可经 SSLVPN 正常连接。

## 共存原则

- 保持 SakuraCat 为 Codex/GitHub 提供所需连接。
- 保持 SSLVPN 连接集群网络，Xshell/Xftp 使用计算服务分配的登录地址。
- 排查某个地址时用单次请求的 direct/proxy 参数，不全局关闭代理、重置网络或随意增删 VPN 路由。
- 若服务方确认网页应从本机直连，再在实际代理规则中对该单个地址设置 DIRECT；但本次 direct 已失败，单纯增加 DIRECT 规则不能作为已解决的证据。

`scripts/windows/check_network.ps1` 会测试同一 URL 的直连与当前系统代理路径，并检查计算集群 SSH 端口；只读诊断，不改代理或 VPN、不提交登录表单。默认报告写入 Git 忽略的 `local/network-report.json`。

## 提供给平台支持的事实

可由用户自行发送：

> 我已连接 SSLVPN，并可通过 SSH/SFTP 正常访问计算集群。调度入口 http://223.108.218.59:3001/login 在本机绕过代理时连接超时，经现有代理返回 502；从集群登录节点直接访问也超时。请核实当前正确入口、3001 端口的服务状态及来源访问控制。

以上不含口令。未替用户联系服务方，也未更改代理/VPN 设置。
