## 已确认的配置生效性差异

直接从生产使用的同一SIF读取TRL和Accelerate源码文件，而非在登录节点运行
模型计算。容器内TRL0.15.2的ppo_trainer.py与固定上游/本机安装文件SHA256一致：
`b3d295d318c8923ecd19ab90898b860c6fdac0408be7f0ab2cd9138ea8e78276`。

实际PPO循环执行loss组合、accelerator.backward、optimizer.step和zero_grad，
整个文件没有读取max_grad_norm或调用梯度范数裁剪。进一步对容器实际
AcceleratedOptimizer.step、Accelerator.backward和accumulate做AST检查，
这些正常单卡路径也未隐式调用梯度范数裁剪。

原YAML配置max_grad_norm=1.0，但该参数未在本轮实际生效。此前将配置数值
直接报告为执行行为不准确，相关文档已更正。梯度范数裁剪与PPO的policy/value
clip=0.2是不同机制；后者在循环中存在。

这尚不能证明它导致了本轮收益弱，四单元都使用同一路径。不应再把
“critic梯度通过全局范数裁剪压制actor”当作当前路径已经成立的解释。
是否加入显式梯度裁剪属于后续新对照，不回头修改原训练记录。

## 接下来的PPO验证

critic为冻结SFT加零初始化的线性value head，当前没有独立critic学习率设置。
应核对实际参数组、梯度、价值拟合与参数增量，不能把value loss较大直接等同
于actor受到压制。按64批、每批2 epoch、每epoch2 mini-batches，静态预期为
256次有效mini-batch更新；64次rollout更新不是64次optimizer.step，后续应记录
实际同步步数，不把静态推算当作动态验收。

原500题配对检查未检出稳定自身Reward提升，见
[已完成的验证](diagnostic-validation-2026-11-15.md)。接下来以固定批次的小规模
受控诊断验证actor更新方向、实际步数、critic拟合和数值路径，再决定学习率或训练量。

## Reward预算：目前不能断言1024不足

训练/留出一致率落差符合过拟合或覆盖不足的现象，也混有Judge噪声、固定线性
特征表达能力和正则影响。没有预算消融，不能确定样本数量是主要原因，或断言
增加预算就会改善泛化。

保持本轮PRISM分布不变，有放回抽样下不同边数期望为sum[1-(1-q)^n]：

| 标签预算n | 期望不同比较边数 |
| --- | ---: |
| 1024 | 270.4 |
| 2048 | 361.7 |
| 4096 | 495.2 |
| 8192 | 706.2 |

扩预算会同时增加重复测量与覆盖，重复测量可以降低噪声，本表不证明预算无效；
它说明标签总数不能直接当作不同设计点数量。Judge和预算是主要控制变量，
还需检查分布覆盖、代理几何及冻结Reward表示，当前不修改它们。
